# 1Hz 前景人脸捕获与每分钟单张照片设计

## 状态

已批准。用户确认以下产品语义：

- YuNet 在后台始终以最多 1Hz 检查最新摄像头帧。
- 绿色框开关只控制实时画面是否显示检测框，不再关闭后台检测。
- 每个自然分钟内，第一次检测到合格前景脸时立即保存当前原始帧。
- 同一分钟后续检测即使仍有人脸，也不再保存第二张照片。
- 下一自然分钟重新允许保存一张。
- 不要求人脸持续出现；只要某次 1Hz 采样命中即可记录。

## 背景

当前摄像头线程持续发布最新帧，但照片和专注状态由默认 60 秒周期的
`monitor_loop()` 抽样。实时绿色框已有独立的 YuNet 1Hz 推理循环，不过
`show_person_box=false` 时该循环停止。因此，人在两个 60 秒抽样点之间短暂
经过时不会留下照片。

现有实时 YuNet 已将最长边缩放到 640 像素，置信度为 `0.50`，只接受面积
至少占画面 `0.5%` 的最大脸。安装版在绿色框开启时整机 CPU 实测平均
`16.27%`。当前 4K 照片平均约 `0.537 MB`，JPEG 编码中位约 `10.5 ms`。

## 目标

1. 将前景人脸检查稳定保持在最多 1Hz，不依赖页面、视频流查看者或绿色框
   开关。
2. 复用同一条 YuNet 推理结果完成实时框和照片触发，禁止增加第二套 1Hz
   检测器。
3. 每个自然分钟最多保存一张照片，并保存命中时的原始分辨率帧。
4. 保留现有前景脸过滤：置信度 `0.50`、面积占比 `0.5%`、只取最大脸、不
   要求正脸。
5. 保持现有专注/离开状态机、两分钟离开宽限、截图周期、历史严格正脸分析
   和 HTTP 响应结构不变。
6. 模型、帧或存储异常不得伪造照片或把检测异常当成离开。

## 非目标

- 不做人脸身份识别。
- 不保证数学意义上覆盖任意恰好一秒的出现；1Hz 是一次每秒的离散采样，
  会受到调度抖动和模型可检测性的影响。
- 不把监控循环、截图或定位查询提升到 1Hz。
- 不在同一分钟保存多张候选照片，也不做“最佳帧”排序。
- 不新增用户设置或性能模式。

## 方案比较

### 方案 A：复用单一、始终运行的 1Hz YuNet 循环（采用）

现有 `face_detection_loop()` 无论绿色框是否开启都执行 YuNet。检测结果用于
两个消费者：

- 若绿色框开启，更新 `state.person_boxes`；关闭时保持框列表为空。
- 若检测到前景脸，非阻塞提交给单消费者照片保存队列；队列再调用共享的
  “每分钟一次”照片保存入口。

优点是无重复推理，绿色框开启时模型 CPU 基本不变；关闭时相比旧行为增加
约一个 1Hz YuNet 通道。缺点是绿色框开关不再是推理总开关，但这正是确保
短暂出现可记录所必需的语义变化。

### 方案 B：保留绿色框循环，另建照片检测循环（拒绝）

两个循环都运行 YuNet，绿色框开启时会重复推理，增加 CPU、模型锁竞争和
结果时序差异，不符合单一高性能策略。

### 方案 C：把整个 monitor 循环提升到 1 秒（拒绝）

会把定位、截图、状态持久化、历史分析及全分辨率检测一并提升到 1Hz，带来
明显 CPU、磁盘和上游调用压力，远超照片捕获需求。

## 详细设计

### 1. 始终运行的 1Hz 检测

`face_detection_loop()` 保留现有 `wait_for_next_inference_start()` 节流和
640 最长边推理。循环只在摄像头帧不可用时空闲等待；不再以
`show_person_box` 决定是否运行模型。

推理完成后：

- 合格框为空：不保存照片，并清空实时框。
- 有一个合格框：把本分钟原始帧非阻塞提交给照片保存队列。
- 模型异常：清空实时框、记录错误、不保存照片；60 秒监控状态仍按现有逻辑
  自行判断，异常不转成可信离开。

绿色框关闭时仍检测和触发照片，但 `state.person_boxes` 始终为空。

### 2. 每分钟照片闸门

在 `take_a_photo.py` 中提供单消费者 daemon 保存队列和线程安全的共享保存
入口。实时 YuNet 循环只负责非阻塞提交，因此 WinRT 定位、JPEG 编码或磁盘
延迟不会暂停 1Hz 推理。队列对 pending 和已成功分钟都去重，然后串行调用
共享保存入口。两层都以捕获时间对应的自然分钟作为键，例如
`20260726_2032`。

保存流程：

1. 1Hz 循环在锁内检查该分钟是否 pending 或已经成功，符合条件时把原始帧
   放入队列后立即返回检测。
2. 单消费者 worker 取出任务，再由共享闸门检查该分钟是否已经成功保存。
3. 如果已保存，立即返回，不做定位、编码或磁盘写入。
4. 如果未保存，使用传入的原始帧创建现有年月日小时目录。
5. 仅在需要保存时获取一次位置；不把定位查询提升到 1Hz。
6. 使用现有 `save_image_with_gps()` 写入 JPEG。
7. 写入成功后记录分钟键并回调更新路径；失败时释放 pending 状态、不记录
   成功分钟，允许本分钟后续新鲜帧命中重试。

现有 60 秒 `take_photo()` 也必须经过同一个闸门。因此实时循环已经保存后，
监控循环不会生成第二张；如果实时循环暂未保存，监控循环仍可成为兜底。

### 3. 状态和历史分析

实时循环保存成功后，在 `state.lock` 下更新 `state.paths["photo"]`。现有
`run_monitor_capture_cycle()` 继续检测新的照片路径，并在下一次 60 秒周期
执行历史严格正脸分析和报告刷新。

截图仍只由原 monitor 周期在可信在场时保存，不跟随 1Hz 照片触发。

### 4. 时间与并发

- 自然分钟按本地系统时间计算，与照片目录和文件名保持一致。
- 分钟闸门使用进程内锁，避免实时循环和 monitor 循环并发重复写入。
- 实时循环与保存队列不共享 `state.lock`；定位和写盘只发生在 worker，
  成功回调才短暂取得 `state.lock` 更新最新照片路径。
- 成功后才占用分钟；异常允许重试。
- 程序在同一分钟重启可能重新保存一张，这是进程重启边界，不引入额外持久化
  状态。若后续需要跨重启严格去重，可另行增加磁盘扫描或状态文件。

## 性能影响

- 绿色框开启：复用当前 1Hz YuNet，模型计算基本不增加。
- 绿色框关闭：旧版本会停止 YuNet；新版本继续 1Hz，当前 32 逻辑处理器机器
  实测约增加 1 个百分点整机 CPU。
- 持续有人时仍最多每分钟一张，磁盘上限与当前行为相同，约 `32 MB/小时`
  或 `0.77 GB/天`。
- 每分钟新增的 JPEG 编码约 `10.5 ms`，且在独立 worker 中执行，不占用
  1Hz YuNet 推理线程。

## 测试

按 TDD 增加以下覆盖：

1. 绿色框关闭时 YuNet 仍按 1Hz 调用，但 `person_boxes` 保持为空。
2. 同一自然分钟连续 60 次命中只保存一张。
3. 下一自然分钟第一次命中可再保存一张。
4. 一分钟前 59 次无脸、最后一次有脸时立即保存。
5. 实时循环与 monitor 同分钟竞争时只产生一个文件。
6. 保存失败不占用分钟，后续命中可以重试。
7. 模型异常不保存照片、清框且不伪造可信离开。
8. 照片保存使用原始帧，不使用 640 推理缩略图。
9. 位置只在实际保存时获取，不按秒调用。
10. 现有两分钟离开宽限、截图周期、严格正脸分析和接口契约保持通过。

## 保存队列背压与退出语义

- 照片保存队列使用单消费者和硬上限 `maxsize=2`。除 worker 正在处理的一张
  原始帧外，最多再持有两张排队原始帧，即进程内最多保留 `active + 2`
  张待保存帧。
- 队列满时丢弃当前候选，不占用该自然分钟的 pending 或 success 状态，也不
  按秒输出错误日志；后续新鲜帧仍可再次尝试提交。
- 显式 `close()` 会拒绝新任务、丢弃尚未开始的排队任务、释放相应帧引用，
  并以幂等方式停止空闲 worker。正在执行的定位或 JPEG 写盘不能被 Python
  安全中断，调用方可在其完成后 join。
- 应用全局 worker 为随进程生命周期运行的 daemon。正常运行不主动关闭它；
  进程退出时允许丢弃尚未完成的队列任务，这与照片捕获的尽力而为语义一致，
  且不会改变 60 秒监控、专注状态或离开宽限。
